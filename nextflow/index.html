What is nf-ccloud?

nf-ccloud is Carolina Cloud's Nextflow executor. It holds a warm pool of workers and resizes them between tasks instead of building and destroying a machine for every process. Same pipelines, same nf-core commands, a fraction of the overhead: nf-core/rnaseq in 4.5 hours for under $20.

How it works: one small driver, and a pool that reshapes itself around your DAG

A run has two roles and they live on different machines. Nothing about this changes how you write a pipeline.

The head runs Nextflow, and nothing else. It runs the Nextflow JVM and the plugin, builds the DAG, submits tasks, and publishes your outdir. It never runs your tools, so it stays small and cheap. Use one of our browser-based head containers, or drive from your own laptop, HPC login node, or CI runner.

The pool sizes workers to the task, not to a menu. Each task is dispatched into a container sized to that process's own cpus, memory, and disk directives. Ask for 6 vCPU and you get 6, and you pay for 6. No rounding up to the nearest instance type, and no standing cluster to keep alive between runs.

The overhead is the whole problem, so we went after the overhead

Most cloud batch systems treat a task in isolation: pick an instance, boot it, run one task, throw it away. On a 300-task nf-core pipeline you pay that tax 300 times.

Resize, don't rebuild. When a process finishes, the worker is not destroyed. It is resized in milliseconds for the next task. A 16 to 64 to 8 vCPU chain is one worker resized twice, with no cold start in between. Between tasks a worker shrinks to a 1 vCPU, 1 GiB idle floor, which is why the pool can afford to stay warm.

Data that is already there. Every worker keeps a persistent local NVMe cache. When a downstream task lands on the worker that produced its inputs, those files are hard-linked in with zero network transfer.

Staging that keeps up. When a file does have to move, s5cmd pulls it in parallel hard enough to saturate our 10 GbE NICs, often around 1 GiB/s.

See inside every run

Every run appears in the console the moment it opens, and the graph fills in live. Nodes repaint as tasks land, the compute cost ticks up in the header, and any task is two clicks from its logs.

  • The live DAG. The graph Nextflow builds internally, rendered as it runs. Click a node for its task list.
  • Allocated against peak. Every task reports the vCPU, RAM, and disk it was given next to what it actually used, so you can find the process asking for 6 GiB and touching 2.
  • The work dir in the browser. Script, stdout, and stderr pinned at the top; reports and plots preview inline.
  • When it fails, the console tells you why. It names the process, the task, and the error, and jumps straight to that task's stderr. "Debug log for LLM" copies a full markdown report (launch command, requested versus peak resources with an OOM flag, staged input sizes, control-file excerpts) to paste into Claude. It never includes your credentials.
  • Cost, live, per task. A ticking compute cost on the DAG header and a cost on every task.
  • A pool that always cleans itself up. Workers are reaped by the platform, so even if the laptop driving the run dies, they tear down and billing stops within a few minutes.
  • Your API key stays on your machine. Runs driven from elsewhere use a scoped, revocable pipeline token that only works on the pipeline endpoints.

Get started

The plugin is in the official Nextflow registry, so there is nothing to download. This is the whole config:

plugins { id 'nf-ccloud@1.0.0' }
process.executor = 'ccloud'

ccloud {
    apiKey   = secrets.CCLOUD_API_KEY
    endpoint = 'https://console.carolinacloud.io'
}

workDir = 's3://YOUR-BUCKET-NAME/work/'

aws {
    accessKey = System.getenv('AWS_ACCESS_KEY_ID')
    secretKey = System.getenv('AWS_SECRET_ACCESS_KEY')
    region    = 'auto'
    client { endpoint = System.getenv('AWS_ENDPOINT_URL') }
}

Then run, keeping -plugins nf-ccloud@1.0.0 on the command line, because nf-core pipelines ship their own plugins block that would otherwise replace yours:

NXF_SYNTAX_PARSER=v1 nextflow run nf-core/rnaseq -r 3.22.2 \
  -plugins nf-ccloud@1.0.0 \
  -profile test \
  --outdir s3://YOUR-BUCKET-NAME/rnaseq-test/results/

Or let your AI do the setup. Paste this into Claude or another assistant: "Please read this: https://console.carolinacloud.io/static/nextflow/local-quickstart.md, and then help me run my first pipeline, starting with nf-core/rnaseq test, and then graduating to a real pipeline." The doc is written for an agent: it installs Nextflow, provisions a bucket, mints credentials, writes the config and launches the run. You supply one API key.

Frequently asked questions

How much does it cost to run nf-core/rnaseq on Carolina Cloud?

$19.26 and 4.5 hours of wall-clock time for 8 human RNA-seq samples (123.3 GiB of gzipped FASTQ), Sentieon-accelerated, using the nf-ccloud executor. The same pipeline cost $45 and took 5.5 hours on AWS HealthOmics; AWS Batch on-demand took 7 to 8 hours and about $70. See the public run.

How do I run a Nextflow pipeline on Carolina Cloud?

Add the nf-ccloud plugin (-plugins nf-ccloud@1.0.0), set process.executor = 'ccloud', and provide your Carolina Cloud API key. The plugin is in the official Nextflow plugin registry, so there is nothing to download. Quickstart.

Do I need to change my pipelines?

No. Same pipelines, same nf-core commands. Each task runs in a container sized to that process's own cpus, memory and disk directives.

Where does the Nextflow head run?

Anywhere Nextflow runs: a browser-based head container in our console, your laptop, an HPC login node, or a CI runner. The head only runs the Nextflow JVM; the heavy tasks never run locally.

What happens if my laptop dies mid-run?

Workers are reaped by the platform, not by the orchestrator, so they still tear down and billing still stops within a few minutes.

Are there egress fees on Nextflow buckets?

No. Nextflow buckets have no minimum retention, consistent read and write speeds, and $0 egress. You can also bring your own S3-compatible bucket.
